智慧門鎖 MQTT 系統架構

把裝置連線（Device Connectivity）與後端業務事件（Backend Domain Event）切成兩層: 前段用 MQTT Broker 撐長連線與 Pub/Sub,後段用內部事件匯流排做 Event-driven, 中間以「指令狀態機 + 應用層冪等」保證開鎖指令不會因重送而重複執行。

.NET 10 MQTT client · MQTTnet 狀態機 · 手寫 enum Broker · EMQX / Mosquitto 內部匯流排 · Kafka / RabbitMQ
分層總覽

四層架構:從鎖端到 downstream

邊緣裝置只認 MQTT;Device Service 是「連線世界」與「內部事件世界」的邊界。 越過這道邊界,MQTT 的裝置訊息就轉成 domain event,由 Kafka／RabbitMQ 扇出給各 consumer—— 兩邊各自伸縮、互不牽動。

命名契約

Topic 分層

Command、Event、Status 走各自的 topic,方向清楚、ACL 好切。 {deviceId} 讓每把鎖天然隔離——ACL 只要綁 locks/{自己的id}/#。

locks/{deviceId}/command 後端→鎖 指令:開／關鎖。載 commandId、TTL,以 QoS 1 發佈
locks/{deviceId}/command/ack 鎖→後端 受理回覆:鎖已收到指令並開始處理(狀態機 → Accepted)
locks/{deviceId}/command/result 鎖→後端 執行結果:成功／失敗 + 錯誤碼(狀態機 → Executed / Failed)
locks/{deviceId}/status 鎖→後端 在線狀態:retained + LWT。斷線時 Broker 代發 offline
可靠性 · 核心設計

一次開鎖指令的生命週期

QoS 1 保證「至少送達一次」,代價是可能重送。開鎖不能執行兩次, 所以真正擋住重複的不是 QoS,而是裝置端的應用層冪等——認 CommandId,不認送達次數。

後端 · 指令狀態機

Command State Machine

後端替每筆指令維護一個明確狀態。查得到「卡在哪一步」,才有辦法對帳、重試與告警—— 而不是只有「發出去了」跟「沒回應」兩種模糊狀態。

連線健康

裝置上線 / 離線偵測

三個機制疊起來,從「TCP 還活著嗎」一路到「後端記得它最後何時出現」,各補一段盲區。

傳輸層

Keep-Alive

裝置定期送 PINGREQ,Broker 回 PINGRESP。 超過 1.5× 週期沒心跳,Broker 判定連線已死並觸發 LWT。抓的是沉默斷線。

Broker 代理

Last Will (LWT)

連線時預先登記遺囑。一旦異常斷線,Broker 自動把 offline 發到 .../status(retained)。裝置來不及說再見時,由 Broker 代發。

應用層

lastSeen

後端訂閱 status 與各回覆,持續更新每把鎖的最後出現時間。 這是給業務查詢與告警用的真實依據,不受單一 Broker 節點狀態影響。

橫切關注 · Security

安全性:分階段上強度

門鎖是實體安全裝置,連線安全不是加分項而是底線。依規模與威脅模型逐級加嚴。

底線

TLS

所有連線加密傳輸,擋住竊聽與竄改。任何情況下的最低要求。

雙向驗證

Device Certificate / mTLS

每把鎖帶自己的憑證,Broker 與裝置互相驗身分。 比帳密更難被複製,單把鎖外洩可單獨撤銷。

最小權限

Topic ACL

每把鎖只能存取 locks/{自己id}/#。 即使一把鎖被攻陷,也碰不到別把鎖的 topic。

生命週期

Credential Rotation

憑證／金鑰定期輪替,並保留撤銷機制。外洩時能快速換發,不必召回硬體。

落地
